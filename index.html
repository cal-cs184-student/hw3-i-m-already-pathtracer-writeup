Part 1: Ray Generation and Scene Intersection

One of the topics of homework 2 was providing shading effects to rendered surfaces with flat shading and then with Phong shading, the latter of which drastically improves the appearance of shadows on curved surfaces. In this homework, we're instead exploring an improved illumination model to simulate global illumination, using a physically-based renderer that implements a pathtracing algorithm. The idea is to trace a ray that originates from the camera viewpoint into various places in the scene, and the ray can reflect off of an object to imitate light reflection or scattering. In part 1, I implemented the very beginning of the rendering pipeline with three steps: pixel sample generation, ray generation, and then ray intersections with primitive shapes, triangles and spheres specifically.

Pixel Sample Generation

In pixel sample generation, we use Monte Carlo integration to estimate the integral of radiance over a given pixel. First, we randomly select ns_aa samples within the pixel with a grid sampler that outputs values between 0 and 1. Then, for each of the samples, we generate a ray traveling to its location and obtain its color, then finally calculate the pixel's final color as an average of all of the samples' colors.

Ray Generation

To generate a ray that points from the camera to a point in the scene, we first have to consider the point in 2D image space as seen from the camera's perspective. This image space is normalized so that a point (x, y) inside it can take on values from (0, 0) to (1, 1), with the image space being centered at (0.5, 0.5). However, the camera space in 3D is centered at (0, 0, -1), and has a width of \( 2*tan(0.5*hFov) \) and a height of \( 2*tan(0.5*vFov) \). See the diagram below.

The ray generation function takes normalized image space coordinates as input, so these values must undergo a composite transformation to be put into camera space. The first transformation is a translation by (-0.5, -0.5), and the second transformation is scaling by \( (2*tan(0.5*hFov), 2*tan(0.5*vFov)) \). The ray begins at the origin, so its direction is determined by the vector that points to this new point at z=-1. Finally, we transform the ray's direction from camera to world space by multiplying it with the given "c2w" matrix, and normalize it. The ray is initialized with this direction and the given camera position in world space.

Detecting Ray-Triangle Intersections

The general process for evaluating a ray-triangle intersection is to determine the point t at which the ray intersects the plane containing the triangle, if that t exists, and then to determine if the ray's intersection point is inside the triangle. I used the Möller Trumbore algorithm for determining if a ray and a triangle intersect, since this enabled me to easily simultaneously calculate the intersection "time" t and the barycentric coordinates of the intersection point. P0, P1, and P2 are the vertices of the triangle, which makes \( b3 = 1 - b1 - b2 \), b1, and b2 their respective barycentric coordinate coefficients. O and D are the ray's origin and direction. Once I calculated all these quantities, I first checked if the denominator term \( \vec{S_1} \cdot \vec{E_1} \) was equal to 0, since this case produces undefined results and means that the ray is parallel to and doesn't intersect the plane containing the triangle. Afterwards, I calculated t and the barycentric coordinates. If t is within the ray's accepted range and the barycentric coordinates are between 0 and 1, this indicates that the intersection point is indeed within the triangle. The intersection test function then returns true and stores the intersection data in the given struct, including t and n, which is the interpolated normal vector of the triangle's plane at the intersection point.

Detecting Ray-Sphere Intersections

To determine the intersection between a sphere and a ray, I used the equations from lecture, which are derived from setting the vector equations for a ray and a sphere equal to each other and structuring it as a quadratic equation, with t as the variable. The constants are given as \( a = d \cdot d, \; \; b = 2(o - c) \cdot d, \; \; c = (o - c) \cdot (o - c) - R^2 \). Therefore, we can simply use the quadratic formula to solve for t. If the determinant in the quadratic is less than 0, t has no solutions and the ray doesn't intersect the sphere; if t has 1 solution, the ray is tangent to the sphere; if t has 2 solutions, the ray intersects the sphere at two points, and the closest intersection point is evaluated. Just as with the triangle, we evaluate the intersection point to determine if it's within the ray's range, and if so, the test function returns true and stores the intersection data, with the stored normal vector simply being the normalized ray from the sphere's center to the intersection point.

Part 2: Bounding Volume Hierarchy

Scenes with a very high number of primitive objects can take a very long time to render, since we must exhaustively test whether or not a ray intersects with each object. Bounding volume hierarchies can vastly accelerate the rendering process -- we can consider each object to be bounded by a volume, and if the ray doesn't intersect with the volume, we know that it therefore won't intersect with the object inside. We can also construct hierarchies of bounding volumes for all primitives, such that a volume closer to the root of the hierarchy fully contains all lower-level child volumes inside of it (see the diagrams below). With these hierarchies, when rendering a scene we can effectively prune the volumes and primitives that need to be evaluated for intersections, because if a parent volume doesn't intersect with the given ray, it is guaranteed that all children will not intersect.

I implemented BVH construction recursively, as suggested in the spec. If the given list of primitives (as pointed to by the start and end pointers) is smaller than the maximum leaf size, then this node becomes a leaf, and the method returns the node. Otherwise, for a non-leaf node, we need to identify which primitives should go into its left and right child nodes, and therefore where to split the list of primitives. I thought of the split point as a sort of "balancing point" for the child nodes and therefore calculated it as the average of the contained primitives' centroids, and then split along the longest axis to hopefully create a more balanced BVH tree. I then identified the midpoint primitive along the splitting axis, and recursively called the function on the two lists of primitives that will be put into the left and right child nodes. I also compared the rendering times for moderately complex .dae files with and without BVH acceleration, creating 800x600 png files and using 8 rendering threads. The file meshedit/beast.dae took 10 minutes and 7 seconds to render without BVH acceleration, and 0.08 seconds with BVH acceleration. meshedit/beetle.dae took 54 seconds without BVH acceleration, and 0.06 seconds with acceleration. meshedit/teapot.dae took 15 seconds without acceleration and 0.08 seconds with acceleration. Across all three examples, there is a massive improvement in rendering time due to BVH acceleration. Creating a BVH for these complex geometries significantly reduces the number of intersection evaluations that must be completed for each ray -- for example, beetle.dae averaged nearly 1,680 intersection tests per ray without BVH acceleration and 1.69 tests per ray with acceleration.
